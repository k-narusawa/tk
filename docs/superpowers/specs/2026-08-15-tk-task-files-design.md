# tk: タスクの詳細を1タスク1ファイルに分離する

2026-08-15

## 背景

[2026-08-13 のタスク詳細メモ](2026-08-13-tk-task-detail-design.md)では、詳細を
「チェックボックス行の直後に続くインデント行」として `tasks.md` の中に持たせた。

これが実際に使ってみて2つの問題を出した。

1. **書くのにインデントの取り決めを覚えている必要がある。** 素直にタスク行の下に
   書くと非インデント行になり、詳細として拾われない。エディタで書いたのに右ペインに
   出ない、という状態になる
2. **`e` は `tasks.md` の該当行を開くだけ**なので、エディタの中は「他のタスクも
   セクション見出しも全部入った1枚のファイル」になる。1つのタスクに集中して書けない

詳細を**タスクごとの独立したファイル**に出し、`e` がそのファイルを直接開くようにする。

あわせて、保存先を `~/tasks.md` から `~/.config/tk/` 配下へ移す。

## 前回「別ファイル案を却下した」判断の取り消し

前回の spec はこう書いて別ファイル案を却下した。

> 別ファイル（`~/.tk/notes/<id>.md`）に持つ案は却下した。`ID` が
> `task:<行番号>` なので、行がずれた瞬間にメモが別のタスクに付く。

この却下理由は**ファイル名に `ID` を使う前提**の上に立っている。本 spec は
ファイル名に**タイトル**を使うので、行がずれても対応は壊れない。却下理由は
今回の設計には当てはまらない。

行番号ベースの `ID` は引き続き `tasks.md` 内の位置指定にだけ使う。

## 保存形式

```
~/.config/tk/
  tasks.md                          一覧。書式は今とまったく同じ
  tasks/
    認証まわりのリファクタ.md          詳細。本文だけ
```

`tasks.md`（変更なし）:

```markdown
- [ ] 認証まわりのリファクタ @today
- [x] 別のタスク
```

`tasks/認証まわりのリファクタ.md`:

```markdown
Cookie の SameSite を Lax に
参考: https://example.com/rfc

RFC を読み直すこと
```

frontmatter は持たせない。完了状態・タグ・並び順はすべて `tasks.md` 側にあり、
詳細ファイルは純粋な本文だけ。詳細ファイルの中身に tk が課す規則はゼロで、
どんな Markdown を書いてもそのまま右ペインに出る。

### なぜ SQLite ではないのか

「完了状態を SQLite で管理する」案を検討して却下した。

- 完了状態が DB に入ると、**Neovim でタスクを完了にできなくなる。** README の
  1行目「Neovim で直接編集してもよい」を壊す。`store.go` がわざわざ symlink を
  解決して Obsidian vault を守っているのと同じ方針に反する
- ファイルを外でリネーム・削除すると DB 行が孤児になる。起動のたびに
  突き合わせが要る。「1タスク = 1ファイル」の利点（ファイルを消せばタスクが
  消える）が DB を足した瞬間に消える
- 依存が増える。cgo（`mattn/go-sqlite3`）はビルド済みバイナリ配布と相性が悪く、
  pure Go（`modernc.org/sqlite`）は依存ツリーが大きい。現状 TUI 以外の依存はゼロ

完了日時・履歴・タグ横断検索が本当に必要になったら、そのときに
**ファイルから再生成できるインデックス**として SQLite を足す。ソースはファイル、
DB はいつ消しても `tk` が作り直せるキャッシュ。この形なら同期の問題は原理的に
起きない。先回りして作らない。

### なぜ frontmatter 方式ではないのか

「`tasks.md` を廃止し、詳細ファイルの frontmatter に `done` / `tag` を持たせる」
案も検討して却下した。重複する情報がゼロになる代わりに、**並び順を持てなくなる**
（ディレクトリにはファイルの順序がない）。今は `tasks.md` の行順がそのまま
並び順になっており、これを失うとルールベースのソートに縛られる。

インデックス方式で重複するのは**タイトル1個だけ**。しかも両方テキストなので、
ズレても Neovim で直せる。

## パスの決め方

| 環境変数 | 既定値 | 用途 |
|---|---|---|
| `TK_TASKS_FILE` | `~/.config/tk/tasks.md` | 一覧の保存先。**既定値だけ変更** |

詳細ディレクトリに専用の環境変数は作らない。`TK_TASKS_FILE` から導出する:

```
拡張子を落としたパス = 詳細ディレクトリ
~/.config/tk/tasks.md  →  ~/.config/tk/tasks/
/tmp/t.md              →  /tmp/t/
```

環境変数が増えず、`TK_TASKS_FILE=/tmp/t.md go run .` が詳細ごと `/tmp/t/` に
隔離される（README の開発手順がそのまま生きる）。

拡張子が無いパス（`/tmp/tasks`）を指定された場合だけ、落とした結果がファイル
自身と衝突する。そのときは `.d` を足して `/tmp/tasks.d/` にする。衝突したまま
`MkdirAll` するとファイルにぶつかって失敗するため。

`config.toml` は作らない。設定は環境変数3つ（`TK_TASKS_FILE` / `TK_AI_CMD` /
`TK_EDITOR`）で足りており、Go 標準ライブラリに TOML parser が無いため
依存を1つ増やすことになる。設定項目が増えて手に負えなくなったら考える。

`~/.config` に置く点について: XDG Base Directory の建前ではデータは
`~/.local/share` が正しい。実際には全部 `~/.config/<app>/` に置くツールが多く、
承知のうえで `~/.config/tk/` に寄せる。**dotfiles リポジトリで `~/.config` を
管理している場合、タスクの中身がリポジトリに入り込む**ので `.gitignore` が要る。

## 読み込み

詳細は**キャッシュしない。** カーソルが動くたびに該当ファイルを1本読む。

- ファイルは数 KB。読むコストは無視できる
- キャッシュしないので、エディタで書き換えれば次に選んだ瞬間に反映される。
  無効化の仕組みが要らない
- ファイルが無ければ空文字を返す。エラーにしない（詳細が無いタスクが普通）
- 読めるがエラー（権限など）なら、右ペインにその旨を出す。PR 詳細の
  取得失敗と同じ扱い

PR 詳細（`usecase.Inbox.Detail`）が無期限キャッシュなのは `gh` のサブプロセス
起動が重いから。ローカルファイル1本の読み込みは事情が違うので、同じ形にしない。

## 書き込み

**tk は詳細を書かない。** この方針は前回から変えない。

`e` を押すと `$EDITOR <詳細ファイル>` が起動する。閉じたら `tasks.md` を
読み直す（今と同じ）。ファイルが存在しなければエディタが新規作成する
（`vi` / `nvim` / `emacs` いずれも存在しないパスを開いて保存できる）。

tk がやる書き込みは**詳細ディレクトリの `mkdir` だけ。** `e` を押した時点で
`os.MkdirAll` する。エディタは親ディレクトリが無いと保存に失敗するため。

行ジャンプが不要になるので `editor.Command` から `+N` 引数が消える。副産物として
**vi 系以外のエディタでも正しく動くようになる**（前回 spec で「行ジャンプが
効かない」と注記した制限が解消する）。

## ファイル名

タイトルをそのままファイル名にし、`.md` を付ける。

| 入力 | 出力 |
|---|---|
| `認証まわりのリファクタ` | `認証まわりのリファクタ.md` |
| `api/auth を直す` | `api-auth を直す.md` |
| `.hidden` | `-hidden.md` |
| 255 バイトを超えるタイトル | バイト単位で切り詰め（UTF-8 の境界を割らない） |

規則:

- `/` と NUL は `-` に置換する。ファイル名に使えないため
- 先頭の `.` は `-` に置換する。隠しファイルになるのを防ぐ
- 前後の空白を落とす
- ファイル名部分が 255 バイトを超えないよう切り詰める。macOS / Linux の
  ファイル名上限。UTF-8 の途中で切らない
- 空文字になったら `_.md` にする（タイトルが `/` だけ、などの病的な入力）
- **タグは含めない。** `- [ ] 認証 @today` のファイル名は `認証.md`。
  タグを付け替えても詳細が迷子にならない

タイトルが `@` を含む正規化は `splitTag` に任せる（既存の挙動をそのまま使う）。

### 同名タスク

`tasks.md` に同じタイトルのタスクが2つあれば、**同じ詳細ファイルを見る。**
片方を編集すればもう片方にも出る。

分けない理由: 同名タスクは元々見分けが付かず紛らわしい。区別するために
サフィックスや ID を導入すると、ファイル名から人が読めなくなり、この設計の
一番の利点を失う。README に書いて済ませる。

### 孤児ファイル

**tk は詳細ファイルを削除しない。** タスクを消す唯一の方法は `tasks.md` を
直接編集することで、そのとき詳細ファイルは残る。

自動削除しない理由: `tasks.md` の行が消えたのが「タスクを完了して消した」のか
「一時的にコメントアウトした」のかを tk は区別できない。書いたメモを勝手に
消すほうが害が大きい。孤児が溜まったら手で消す。

起動時の警告も出さない。「詳細ファイルはあるが `tasks.md` に行が無い」は
正常な状態（下書き、消したタスクの記録）でもありうる。

## 影響範囲

### `internal/domain`

- **`bodyAt` / `dedent` を削除。** インデント行はもう詳細ではない
- `task.body` フィールドを削除
- **`Item.Body` も削除する。** 詳細はファイルから読むので、一覧の `Item` に
  詰める必要がない。右ペインは表示のときだけ本文を取る（下の usecase 参照）。
  `detailText` は本文を引数で受け取る形に変える
- `TaskList.Add` の挿入位置ロジックを見直す。今は「最後のタスクの詳細行の末尾」に
  挿入しているが、詳細行がなくなるので「最後のチェックボックス行の直後」で足りる
- `Parse` → `Render` のバイト一致は**維持**。既存のテストをそのまま通す
- `ID` は `task:<行番号>` のまま。変更なし

既存の `tasks.md` にインデント行が残っていても `Render` がバイト一致で保つので
消えない。右ペインに出なくなるだけ。

### `internal/adapter/markdown`（新規追加）

詳細ファイル用に**別の型 `DetailStore` を足す。** 既存の `Store` には生やさない。
`Store` は `mtime` / `size` の状態を持ち並行呼び出しが安全でないのに対し、
`DetailStore` は状態を持たず読むだけなので、混ぜると `Store` の制約が
広がってしまう。

- ファイル名の sanitize（上の規則）
- タイトル → 本文の読み込み。無ければ空文字
- 詳細ディレクトリの `MkdirAll`

### `internal/usecase`

- ポート `TaskDetailStore` を1つ足す

  ```go
  // TaskDetailStore はタスク1件ぶんの詳細ファイル。adapter/markdown が実装する。
  type TaskDetailStore interface {
      // Body は詳細の本文。ファイルが無ければ空文字を返し、エラーにしない。
      Body(title string) (string, error)
      // EditPath は e が開くパス。親ディレクトリが無ければ作る。
      EditPath(title string) (string, error)
  }
  ```

- `Inbox.Body(id domain.ID) (string, error)` と
  `Inbox.DetailPath(id domain.ID) (string, error)` を足す。どちらも `id` から
  タイトルを引いて `TaskDetailStore` に委譲する
- **`Inbox.Tasks()` は本文を詰めない。** 一覧に本文は要らないので、全件ぶん
  ファイルを開くのは無駄。TUI が選択中の1件だけ `Inbox.Body(id)` で取る

### `internal/adapter/editor`

- `Command(editorCmd, path string, line int)` から `line` を落として
  `Command(editorCmd, path string)` にする

### `internal/adapter/tui`

- `editExec` が `Inbox.DetailPath(id)` の結果を `editor.Command` に渡す
- `syncDetail` が選択中タスクの本文を `Inbox.Body(id)` で読み、`detailText` に渡す。
  読み込みエラーは右ペインに出す（PR 詳細の取得失敗と同じ扱い）
- `Config.TasksFile` は削除した。参照している production コードが無く、`R` の再読み込みは `Inbox.Load` が、パスの保持は `Store` が担う

### `main.go`

- `tasksPath()` の既定値を `~/.config/tk/tasks.md` に変更
- 詳細ストアを組み立てて `usecase.NewInbox` に渡す

## 移行

**自動移行はしない。** ユーザーのファイルを勝手に動かさない。

README に手順を書く:

```sh
mkdir -p ~/.config/tk
mv ~/tasks.md ~/.config/tk/tasks.md
```

既存のインデント詳細は `tasks.md` にそのまま残る（`Render` がバイト一致で保つ）。
右ペインに出したければ `~/.config/tk/tasks/<タイトル>.md` に手で移す。

旧パスへのフォールバックも入れない。既定値を変えるだけにして、
`~/tasks.md` を使い続けたい場合は `TK_TASKS_FILE` で明示する。

## テスト

新規:

- ファイル名 sanitize: `/`、先頭 `.`、255 バイト超、空文字、タグを含むタイトル
- 詳細の読み込み: 存在する / 存在しない / ディレクトリごと存在しない
- 詳細ディレクトリの導出: `~/.config/tk/tasks.md` → `~/.config/tk/tasks/`、
  拡張子なしのパス
- `editor.Command` のシグネチャ変更ぶん

削除:

- `bodyAt` / `dedent` のテスト一式

維持:

- `Parse` → `Render` のバイト一致
- `Toggle` / `Add` / `SortTasks`

テストは標準の `testing` のみ。フレームワークは足さない。

## スコープ外

- **タスクの削除機能。** `tasks.md` を直接編集する今のやり方を変えない
- **タイトル変更時のファイル自動リネーム。** タイトルを TUI から編集する機能が
  そもそも無い。`n` で追加するだけ
- **孤児ファイルの検出・掃除コマンド。** 手で消せば足りる
- **SQLite インデックス。** 上に書いたとおり、必要になってから
- **`config.toml`。** 環境変数で足りている
- **詳細ファイルの全文検索。** `rg ~/.config/tk/tasks/` で足りる
