# tk — 統合インボックス TUI 設計

作成日: 2026-08-11

> この設計はタスク / GitHub のタブ分割より前のもの。差分は [2026-08-12-tk-tabs-design.md](2026-08-12-tk-tabs-design.md) を参照。

## 目的

日々のタスクと GitHub の PR を1つのインボックスにまとめ、ターミナルから
離れずに「今日やること」を決められるようにする。整理作業は外部の AI CLI に
渡して手伝わせる。

## スコープ

**含む**

- 自作タスクの管理（Markdown ファイル）
- GitHub PR の一覧表示（レビュー依頼された PR + 自分が author の PR）
- 選択中アイテムを外部 AI CLI に渡す
- lazygit 風の2ペイン UI（左リスト / 右詳細）

**含まない（意図的に外した）**

- Jira 連携。将来やる予定はあるが、今回は認証も含めてスコープ外。
  追加するときは `usecase.PRSource` と同じ形のポートを1つ足し、
  `adapter/jira` に実装を置けばよい設計にしてある。
- PR のマージ・approve・コメント投稿。破壊的操作は `gh` とブラウザに任せる。
- パネル間のフォーカス移動。左リスト固定にする。
- 設定ファイル。環境変数2つで足りる。

## アーキテクチャ

`adapter` / `usecase` / `domain` の3層に分ける。依存の矢印は
**adapter → usecase → domain の一方向**で、逆流させない。

```
github.com/k-narusawa/tk
  main.go                    環境変数読み → DI配線 → tea.NewProgram

  domain/                    外部ライブラリ import ゼロ
    item.go                  Item, Kind, ID, Role, PRDetail
    tasklist.go              Parse / Render / Toggle / Add
    tasklist_test.go
    inbox.go                 PR の重複排除 + 並び順
    inbox_test.go

  usecase/                   domain のみに依存
    port.go                  TaskStore / PRSource / PRDetailSource
    inbox.go                 Inbox（Load, Refresh, Toggle, Add, Detail）
    inbox_test.go

  adapter/
    tui/                     bubbletea への依存はここだけ
      model.go
      update.go
      view.go
    markdown/store.go        TaskStore 実装（ReadFile / tmp+Rename）
    gh/pr.go                 PRSource 実装（gh search prs）
    gh/pr_test.go
    gh/detail.go             PRDetailSource 実装（gh pr view）
    gh/cmd.go                gh pr diff の *exec.Cmd 組み立てと gh pr view --web の実行
    ai/ai.go                 一時ファイル書き出し → *exec.Cmd
    ai/ai_test.go
```

`main.go` だけが全層を知る。各 adapter は自分が実装するポート以外を知らない。

### 各層の責務

**domain** — tk の言葉そのもの。`Item` の構造、Markdown チェックボックスの
解釈と生成、インボックスの並び順。すべて純粋関数で、`strings` と `fmt` 以外を
import しない。テストにファイルもネットワークも要らない。

Markdown 形式を domain に置くのは、あの形式が単なる保存フォーマットではなく
**ユーザーと交わした約束**だから。Neovim で直接編集できること、AI CLI に
ファイルパスを渡すだけで内容を理解させられることが要件に含まれている。

**usecase** — アプリの手順。ファイルを読んで PR を混ぜてインボックスを組む、
タスクを完了にして保存する、PR の詳細を必要になった時点で取ってキャッシュする。
ポートの interface を**自分で定義**し、実装は知らない。

**adapter** — 外の世界との接点。TUI、`gh` サブプロセス、ファイル I/O、
外部 AI CLI の起動。

### 依存

```
charm.land/bubbletea/v2 v2.0.8   → adapter/tui と main.go
charm.land/lipgloss/v2  v2.0.5   → adapter/tui のみ
charm.land/bubbles/v2   v2.1.1   → adapter/tui のみ（viewport, textinput）
```

`main.go` が `tea.NewProgram` を呼ぶため bubbletea を import する。これは
「`main.go` だけが全層を知る」という原則の範囲内として許容する。
`adapter/tui` に `Run()` を作って隠すこともできるが、配線層が実行方法を
知っていること自体は問題ではないと判断した。レンダリング（lipgloss）と
ウィジェット（bubbles）は `adapter/tui` の外に出さない。

**モジュールパスは `charm.land/...`**。v2 で `github.com/charmbracelet/...` から
移行しており、旧パスでは `go get` が通らない。Go は 1.26 以降。

domain と usecase は標準ライブラリだけで動く。

### bubbletea v2 の API（v1 と違う点）

実際に v2.0.8 でコンパイル確認済み。v1 の記憶で書くと通らない箇所がある。

| 項目 | v2 |
|---|---|
| View の戻り値 | `View() tea.View`（`string` ではない）。`tea.NewView(s)` で作る |
| altscreen | `tea.WithAltScreen()` オプションではなく `view.AltScreen = true` |
| キー入力 | `tea.KeyPressMsg`（`tea.KeyMsg` ではない）。`msg.String()` で分岐する |
| スペースキー | `msg.String()` は `"space"`（`" "` ではない）。実測で確認済み |
| Update | `Update(tea.Msg) (tea.Model, tea.Cmd)` |
| viewport 生成 | `viewport.New(viewport.WithWidth(w), viewport.WithHeight(h))`（位置引数ではない） |
| viewport のサイズ変更 | `SetWidth(w)` / `SetHeight(h)` |
| textinput の幅 | `SetWidth(w)`（`Width` フィールドではない） |
| textinput のカーソル | `m.input.Cursor()` が `*tea.Cursor`。`view.Cursor` に代入して表示する |
| 右ペインのスクロール | `HalfPageDown()` / `HalfPageUp()` |

GitHub へのアクセスは `gh` CLI をサブプロセスで叩く。自前の API クライアントも
トークン管理も持たない。`gh` が既にログイン済みの認証情報を使う。

### 設定

設定ファイルは作らない。環境変数2つ。`main.go` で読む。

| 変数 | 既定値 | 用途 |
|---|---|---|
| `TK_TASKS_FILE` | `~/tasks.md` | タスクの保存先 |
| `TK_AI_CMD` | `claude` | `a` キーで起動する AI CLI |

## データ表現

### Item

タスクと PR を1つのリストに混ぜて表示するため、共通の構造体を1つ持つ。
interface + 2実装より、両方のフィールドを持った struct 1つのほうが小さい。
種類が3つ4つに増えたら、そのとき分割を考える。

```go
package domain

type Kind int

const (
    KindTask Kind = iota
    KindPR
)

type Role string

const (
    RoleReview Role = "review" // レビューを依頼された
    RoleMine   Role = "mine"   // 自分が author
)

// ID は "task:3" / "pr:app/payment#412" の形。
type ID string

type Item struct {
    ID    ID
    Kind  Kind
    Title string

    // KindTask のみ
    Done bool
    Tag  string // "@today" など

    // KindPR のみ
    Repo   string
    Number int
    URL    string
    Role   Role
}
```

`ID` で識別する。元案にあった `LineNo`（`tasks.md` の行番号）は持たない。
行番号は書き戻しのための実装詳細であり、`Item` に載せると adapter の都合が
domain に漏れる。行との対応は `TaskList` の内部だけが知る。

### PRDetail

一覧に載せない重い情報。右ペインに表示するときだけ取得する。

```go
type PRDetail struct {
    CI       string // "passing" / "failing" / "pending" / ""
    Reviews  string // "2人待ち" など
    Additions, Deletions, ChangedFiles int
}
```

### TaskList

`tasks.md` の全行と、そこから解釈した `Item` を対で持つ。

```go
type TaskList struct {
    lines []string // 元ファイルの全行（原文のまま）
    tasks []task   // lines へのインデックスを持つ
}

func Parse(lines []string) TaskList
func (t TaskList) Items() []Item
func (t TaskList) Render() []string
func (t TaskList) Toggle(id ID) TaskList
func (t TaskList) Add(title string) TaskList
```

`Toggle` と `Add` は新しい `TaskList` を返す。元を書き換えないので、
書き込みに失敗したときに状態が壊れない。

### tasks.md の形式

GitHub Flavored Markdown のチェックボックス。

```markdown
# 仕事

- [ ] 設計レビューの返信 @today
- [ ] 1on1の準備 @2026-08-12
- [x] 決済バグの再現手順を書く

## メモ
ここは自由記述。tk は解釈しないが、消しもしない。
```

`- [ ] ` / `- [x] ` で始まる行だけを `Item` にする。それ以外の行（見出し・
空行・自由記述）は**原文のまま `lines` に保持**し、`Render` で元の位置へ戻す。

## ポート

```go
package usecase

type TaskStore interface {
    Load() (domain.TaskList, error)
    Save(domain.TaskList) error
}

type PRSource interface {
    Fetch(ctx context.Context, role domain.Role) ([]domain.Item, error)
}

type PRDetailSource interface {
    Detail(ctx context.Context, repo string, number int) (domain.PRDetail, error)
}
```

interface はこの3つだけ。`Fetch` は role を1つ受けて `gh` を1回叩く。
**2本のクエリを並行に走らせて重複排除するのは usecase の仕事**にする。
こうすると「両方に現れた PR は `review` を優先する」というルールを
fake ポートで検証できる。

## Inbox（usecase）

```go
type Inbox struct {
    store   TaskStore
    prs     PRSource
    details PRDetailSource

    tasks   domain.TaskList
    prItems []domain.Item
    cache   map[string]domain.PRDetail
}
```

| メソッド | 動作 |
|---|---|
| `Load()` | `store.Load()` を呼ぶ。失敗したらエラーを返す |
| `Items()` | タスク + PR を `domain.SortInbox` に通して返す |
| `Refresh(ctx)` | 2つの role を並行に `Fetch` → `domain.MergePRs` で重複排除 |
| `Toggle(id)` | `tasks.Toggle(id)` → `store.Save` → 成功したら自身を更新 |
| `Add(title)` | 同上 |
| `Detail(ctx, id)` | キャッシュを見て、無ければ `details.Detail` を呼び入れる |

`Detail` のキャッシュを usecase に置くのは、「右ペインに表示するときに初めて
取る」がアプリの方針であって `gh` の都合ではないから。起動時に全 PR ぶん
叩かないという性能上の約束を、fake ポートの呼び出し回数として検証できる。

<!-- ponytail: キャッシュは map で無期限。件数が数十を超えて体感が悪ければ、
     先頭 N 件だけ先読みするか、GraphQL で1リクエストにまとめる -->

すべて同期メソッドにする。非同期にするかどうかは `adapter/tui` が
`tea.Cmd` で包むときに決める。usecase は goroutine を知らない
（`Refresh` 内部の2本並行を除く）。

## 画面

左 40% がインボックス、右 60% が選択中アイテムの詳細。lipgloss の
`JoinHorizontal` で並べ、`tea.WindowSizeMsg` で幅を割り振る。

```
┌ Inbox ────────────────┐┌ Detail ──────────────────┐
│ □ 設計レビューの返信    ││ #412 fix: 決済のnull落ち  │
│>#412 fix: 決済のnull    ││                          │
│ #409 feat: 在庫API     ││ repo   : app/payment     │
│ □ 1on1の準備           ││ CI     : ✓ passing       │
│ ▣ 再現手順を書く       ││ review : 2人待ち          │
│                       ││ +124 -31 (5 files)       │
└───────────────────────┘└──────────────────────────┘
 j/k:移動 space:完了 n:追加 enter:開く d:diff a:AI r:更新 q:終了
```

フォーカスは**常に左リストに固定**する。lazygit のようなパネル間移動は
実装しない。右ペインが長いときは `ctrl+d` / `ctrl+u` でスクロールするだけに
すれば、フォーカス状態の管理コードが丸ごと不要になる。

### tui の Model

```go
type Model struct {
    inbox *usecase.Inbox

    items    []domain.Item
    cursor   int
    detail   viewport.Model
    input    textinput.Model
    adding   bool
    errMsg   string
    width, height int
}
```

`domain.Item` をそのまま持ち、View で描画する。層ごとの DTO 変換と
Presenter は作らない。

### キーバインド

| キー | 動作 |
|---|---|
| `j` / `k` | カーソル移動（右ペインは自動追従） |
| `space` | タスクの完了トグル → `tasks.md` へ即書き戻し |
| `n` | 新規タスク入力（textinput を下部に出す） |
| `enter` | PR をブラウザで開く（`gh pr view --web`）。タスクでは何もしない |
| `d` | `gh pr diff` をページャで表示 |
| `a` | 選択アイテムを AI CLI に渡す |
| `A` | インボックス全体を AI CLI に渡す |
| `r` | PR を再取得 |
| `R` | `tasks.md` を再読み込み（外部エディタで編集したあとに使う） |
| `ctrl+d` / `ctrl+u` | 右ペインのスクロール |
| `q` | 終了 |

## データフロー

### 起動

`main.go`:

1. 環境変数を読む
2. `markdown.NewStore(path)`, `gh.NewPRSource()`, `gh.NewDetailSource()` を作る
3. `usecase.NewInbox(...)` に渡す
4. `inbox.Load()` を**同期で**呼ぶ。失敗したらここで終了する
5. `tui.New(inbox)` を `tea.NewProgram` に渡して走らせる
6. `Init()` が返す `tea.Cmd` で `inbox.Refresh(ctx)` を走らせる

タスクは同期で読むので即座に描画できる。PR の取得は待たない。返ってきたら
`prLoadedMsg` で `items` を差し替えて再描画する。ネットワークが遅くても
TUI は即座に立ち上がる。

### PR の取得（usecase.Refresh）

`adapter/gh` は role ごとに1本のクエリを投げる。

```
gh search prs --state=open --review-requested=@me --json number,title,repository,url
gh search prs --state=open --author=@me           --json number,title,repository,url
```

usecase が2本を goroutine で並行に走らせ、両方揃ったら
`domain.MergePRs(review, mine)` に渡す。`MergePRs` は `repo` と `number` で
重複排除し、`Role` は `review` を優先する純粋関数。

CI 状態とレビュー状況は `gh search prs` の JSON に含まれない。
`inbox.Detail(ctx, id)` が呼ばれたとき（= 右ペインに表示するとき）に
`gh pr view --json statusCheckRollup,reviewRequests,additions,deletions,changedFiles`
を投げて補完し、`cache` に入れる。起動時に全 PR ぶん叩くことはしない。

### タスクの書き戻し

`space` でトグルしたら即座にファイルへ書く。

1. `domain`: `tasks.Toggle(id)` が新しい `TaskList` を返す。
   対象行の `[ ]` ↔ `[x]` だけが差し替わり、他の行は原文のまま
2. `adapter/markdown`: `Render()` の結果を一時ファイルに書く
3. `os.Rename` で元ファイルに被せる（atomic）
4. 成功したら usecase が自身の `tasks` を新しいものに差し替える

途中でプロセスが死んでもファイルが壊れない。書き込みが失敗した場合は
`tasks` を更新しないので、画面とファイルが食い違わない。

`Add` した新規タスクは、**`lines` 内の最後のチェックボックス行の直後**に
挿入する。末尾に追記すると `## メモ` のような後続セクションの下に紛れ込んで
しまうため。チェックボックス行が1つも無いファイル（または空ファイル）なら
末尾に追記する。

### 並び順（domain.SortInbox）

ソートキーは固定で、ユーザーが変更する手段は用意しない。

1. 未完了タスク（`tasks.md` に書かれている順）
2. レビュー依頼された PR（`Role == RoleReview`）
3. 自分の PR（`Role == RoleMine`）
4. 完了済みタスク

自分で書いた順序に意味があるのでタスクは並べ替えない。PR は「他人を待たせて
いるもの」が先に来るようにする。

### 外部プロセスの起動

`d`（diff）と `a`（AI）は `tea.ExecProcess` を使う。TUI を一旦畳んで
ターミナルを子プロセスに明け渡し、終了したら TUI に戻る。ページャや
`claude` の対話画面がそのまま使える。

bubbletea への依存を `adapter/tui` に閉じ込めるため、
**`adapter/ai` と `adapter/gh` は `*exec.Cmd` を返すだけ**にする。
`tea.ExecProcess` で包むのは tui の仕事。

```go
// adapter/ai
func Command(aiCmd string, items []domain.Item) (*exec.Cmd, error)

// adapter/gh
func DiffCommand(repo string, number int) *exec.Cmd
func WebCommand(repo string, number int) *exec.Cmd

// adapter/tui/update.go
cmd, err := ai.Command(m.aiCmd, []domain.Item{m.items[m.cursor]})
if err != nil {
    m.errMsg = err.Error()
    return m, nil
}
return m, tea.ExecProcess(cmd, aiDoneMsg)
```

`ai.Command` は選択中アイテムの内容（タスクなら本文、PR ならタイトル・URL・
CI 状態）を一時ファイルに書き、`$TK_AI_CMD <一時ファイルパス>` の
`*exec.Cmd` を返す。インボックス全体を渡す `A` は同じ関数に全アイテムを
渡すだけ。TUI を起動しなくても一時ファイルの内容をテストできる。

`enter`（`gh.WebCommand`）だけは `tea.ExecProcess` を使わない。ブラウザを
起動して即座に終了するだけで、ターミナルを明け渡す必要がないため。
`tea.Cmd` の中で `cmd.Run()` を呼び、エラーだけ `errMsg` に載せる。

## エラー処理

ここは削らない。

| 状況 | 挙動 |
|---|---|
| `gh` が PATH に無い | `adapter/gh` がエラーを返す。tui が下部バーに1行表示。タスク側は通常どおり動く |
| `gh` が未ログイン | 同上。`gh` の stderr をそのまま `error` に含める |
| `gh` がタイムアウト | `context.WithTimeout` 10秒で打ち切り、エラー表示。`r` で再試行できる |
| `tasks.md` が無い | 空の `TaskList` で起動。最初の `Save` で作成する |
| `tasks.md` が読めない（権限等） | `main.go` の `inbox.Load()` でエラー。**起動を中止する**。空リストで起動すると、書き戻し時に既存の内容を消しかねない |
| `Save` が失敗 | usecase は `tasks` を更新せずエラーを返す。tui が下部バーに表示。画面とファイルが食い違わない |
| **起動中に `tasks.md` が外部で変更された** | `Save` 直前に mtime / size を確認し、変わっていたら**上書きせずエラー**を返す。下部バーに「`R` で再読み込みしてください」と出す。外部エディタでの編集を無音で消さないこと。tk は起動時に1回しか読まないため、この確認が無いと `space` 1回で外部の変更が全て消える |
| パースできない行 | `Item` にせず `lines` に原文のまま保持し、`Render` で元の位置へ復元する |

PR の取得失敗でアプリを落とさない。タスク管理は GitHub と無関係に成立する。

## テスト

標準の `testing` のみ。テストフレームワークは足さない。

| 対象 | 内容 |
|---|---|
| `domain/tasklist_test.go` | **round-trip**: 見出し・空行・自由記述を含むファイルを `Parse` → `Render` して1バイトも変わらないこと。**toggle**: 対象行の `[ ]` だけが `[x]` になり他の行が無傷なこと。**add**: 末尾のリストブロックに追記され後続の見出しが壊れないこと。**add（チェックボックス無し）**: 空ファイル・見出しだけのファイルで末尾に追記されること |
| `domain/inbox_test.go` | `SortInbox` の並び順。`MergePRs` の重複排除と `review` 優先 |
| `usecase/inbox_test.go` | fake ポートで、`Load` 後に `Detail` を呼ぶまで `PRDetailSource` が0回しか呼ばれないこと。同じ ID を2回引くと1回しか呼ばれないこと。`Save` 失敗時に `tasks` が変わらないこと |
| `adapter/gh/pr_test.go` | `gh search prs` の JSON サンプル → `[]domain.Item` 変換 |
| `adapter/ai/ai_test.go` | 一時ファイルの内容と `*exec.Cmd` の引数 |
| `adapter/markdown` | atomic write の性質を押さえる。round-trip がバイト一致すること、権限が維持されること、一時ファイルが残らないこと、外部で変更されていたら上書きせずエラーにすること。`Parse`/`Render` のロジック自体は domain 側でテストする |
| `adapter/tui` | 端末なしで `Update` に合成メッセージを流し、モデルの状態と描画結果を検証する。当初は「テストなし。壊れたら起動すれば分かる」方針だったが、実際には最も多くの欠陥がここで見つかったため方針を変えた。特に押さえるべき性質: キーが実際に発火すること（`space` は `msg.String()` が `"space"`）、描画が端末の幅と高さに収まること、左右ペインの高さが揃うこと、エラー表示が別の発生源に消されないこと |

domain のテストはファイル I/O もネットワークも使わない純粋関数テストになる。

## 実装順序

1. `domain/item.go` + `domain/tasklist.go` + テスト（土台。ここが一番大事）
2. `usecase/port.go` + `usecase/inbox.go`（`TaskStore` のみ配線）+ テスト
3. `adapter/markdown/store.go` + `adapter/tui` 最小版 + `main.go`
   → タスクだけ表示・トグル・追加できる
4. `domain/inbox.go` + `adapter/gh/pr.go` + テスト（PR をリストに混ぜる）
5. 右ペインの詳細表示 + `adapter/gh/detail.go`（遅延補完 + キャッシュ）
6. `adapter/ai` + `adapter/gh/cmd.go` + `enter` / `d` / `a` / `A` キー

3 の時点で「Markdown タスク管理 TUI」として実用になる。そこで一度使ってみて、
4 以降の優先度を決め直せる。
