# tk — 統合インボックス TUI 設計

作成日: 2026-08-11

## 目的

日々のタスクと GitHub の PR を1つのインボックスにまとめ、ターミナルから
離れずに「今日やること」を決められるようにする。整理作業は外部の AI CLI に
渡して手伝わせる。

## スコープ

**含む**

- 自作タスクの管理（Markdown ファイル）
- GitHub PR の一覧表示（レビュー依頼された PR + 自分が author の PR）
- 選択中アイテムを外部 AI CLI に渡す
- lazygit 風の2ペイン UI（左リスト / 右詳細）

**含まない（意図的に外した）**

- Jira 連携。将来やる予定はあるが、今回は認証も含めてスコープ外。
  追加するときは `jira.go` を1つ足して `[]Item` を返せばよい設計にしてある。
- PR のマージ・approve・コメント投稿。破壊的操作は `gh` とブラウザに任せる。
- ベルトの向き……ではなく、パネル間のフォーカス移動。左リスト固定にする。
- 設定ファイル。環境変数2つで足りる。

## 全体構成

```
github.com/k-narusawa/tk
  main.go          エントリ（環境変数読み → tea.NewProgram）
  item.go          Item 型（タスクと PR の共通表現）
  task.go          tasks.md のパース・書き戻し
  github.go        gh 呼び出し → []Item
  ui.go            Model / Update / View
  ai.go            外部 AI CLI の起動
  task_test.go     パースの round-trip テスト
  github_test.go   gh JSON → Item 変換テスト
```

依存は3つだけ。

- `github.com/charmbracelet/bubbletea/v2` — TUI ランタイム
- `github.com/charmbracelet/lipgloss/v2` — 枠線・レイアウト
- `github.com/charmbracelet/bubbles/v2` — viewport（右ペインのスクロール）、
  textinput（新規タスク入力）

GitHub へのアクセスは `gh` CLI をサブプロセスで叩く。自前の API クライアントも
トークン管理も持たない。`gh` が既にログイン済みの認証情報を使う。

### 設定

設定ファイルは作らない。環境変数2つ。

| 変数 | 既定値 | 用途 |
|---|---|---|
| `TK_TASKS_FILE` | `~/tasks.md` | タスクの保存先 |
| `TK_AI_CMD` | `claude` | `a` キーで起動する AI CLI |

## データ表現

タスクと PR を1つのリストに混ぜて表示するため、共通の構造体を1つ持つ。
interface + 2実装より、両方のフィールドを持った struct 1つのほうが小さい。
種類が3つ4つに増えたら、そのとき分割を考える。

```go
type Kind int

const (
    KindTask Kind = iota
    KindPR
)

type Item struct {
    Kind  Kind
    Title string

    // KindTask のみ
    Done   bool
    Tag    string // "@today" など
    LineNo int    // tasks.md の行番号（書き戻し用）

    // KindPR のみ
    Repo    string
    Number  int
    URL     string
    CI      string // "passing" / "failing" / "pending" / ""
    Reviews string // "2人待ち" など
    Role    string // "review"（依頼された） / "mine"（自分の）
}
```

### tasks.md の形式

GitHub Flavored Markdown のチェックボックス。TUI を使わずに Neovim で直接
編集できること、AI CLI にファイルパスを渡すだけで内容を理解させられることを
狙っている。

```markdown
# 仕事

- [ ] 設計レビューの返信 @today
- [ ] 1on1の準備 @2026-08-12
- [x] 決済バグの再現手順を書く

## メモ
ここは自由記述。tk は解釈しないが、消しもしない。
```

`- [ ] ` / `- [x] ` で始まる行だけを `Item` にする。それ以外の行（見出し・
空行・自由記述）は**原文のまま保持**し、書き戻し時に元の位置へ戻す。

## 画面

左 40% がインボックス、右 60% が選択中アイテムの詳細。lipgloss の
`JoinHorizontal` で並べ、`tea.WindowSizeMsg` で幅を割り振る。

```
┌ Inbox ────────────────┐┌ Detail ──────────────────┐
│ □ 設計レビューの返信    ││ #412 fix: 決済のnull落ち  │
│>#412 fix: 決済のnull    ││                          │
│ #409 feat: 在庫API     ││ repo   : app/payment     │
│ □ 1on1の準備           ││ CI     : ✓ passing       │
│ ▣ 再現手順を書く       ││ review : 2人待ち          │
│                       ││ +124 -31 (5 files)       │
└───────────────────────┘└──────────────────────────┘
 j/k:移動 space:完了 n:追加 enter:開く d:diff a:AI r:更新 q:終了
```

フォーカスは**常に左リストに固定**する。lazygit のようなパネル間移動は
実装しない。右ペインが長いときは `ctrl+d` / `ctrl+u` でスクロールするだけに
すれば、フォーカス状態の管理コードが丸ごと不要になる。

### キーバインド

| キー | 動作 |
|---|---|
| `j` / `k` | カーソル移動（右ペインは自動追従） |
| `space` | タスクの完了トグル → `tasks.md` へ即書き戻し |
| `n` | 新規タスク入力（textinput を下部に出す） |
| `enter` | PR をブラウザで開く（`gh pr view --web`）。タスクでは何もしない |
| `d` | `gh pr diff` をページャで表示 |
| `a` | 選択アイテムを AI CLI に渡す |
| `A` | インボックス全体を AI CLI に渡す |
| `r` | PR を再取得 |
| `ctrl+d` / `ctrl+u` | 右ペインのスクロール |
| `q` | 終了 |

## データフロー

### 起動

1. `tasks.md` を**同期で**読んで `[]Item` にする
2. すぐに描画する（PR の取得を待たない）
3. `tea.Cmd` で `gh` を2本並行に走らせる
4. 返ってきたら `prLoadedMsg` でマージして再描画

ネットワークが遅くても TUI は即座に立ち上がる。PR は後から差し込まれる。

### PR の取得

全リポジトリ横断で2本のクエリを投げる。

```
gh search prs --state=open --review-requested=@me --json number,title,repository,url
gh search prs --state=open --author=@me           --json number,title,repository,url
```

CI 状態とレビュー状況は `gh search prs` の JSON に含まれないため、一覧が
返ってきたあとに各 PR へ `gh pr view --json statusCheckRollup,reviewRequests`
を投げて補完する。件数が多いと重いので、**この補完は「右ペインに表示する
とき」に遅延実行し、結果をメモリにキャッシュする**。起動時に全 PR ぶん
叩くことはしない。

<!-- ponytail: 補完は選択時の遅延実行。件数が数十を超えて体感が悪ければ、
     先頭 N 件だけ先読みするか、GraphQL で1リクエストにまとめる -->

両方のクエリに現れた PR（自分の PR に自分がレビュー依頼されている等）は
`number` と `repo` で重複排除し、`Role` は `review` を優先する。

### タスクの書き戻し

`space` でトグルしたら即座にファイルへ書く。手順は以下。

1. 元ファイルの全行を保持した状態で、対象行の `[ ]` ↔ `[x]` だけ差し替える
2. 一時ファイルに全文を書く
3. `os.Rename` で元ファイルに被せる（atomic）

途中でプロセスが死んでもファイルが壊れない。

`n` で追加した新規タスクは、**ファイル内の最後のチェックボックス行の直後**に
挿入する。末尾に追記すると `## メモ` のような後続セクションの下に紛れ込んで
しまうため。チェックボックス行が1つも無いファイル（または空ファイル）なら
末尾に追記する。

### 並び順

インボックスは以下の順で並べる。ソートキーは固定で、ユーザーが変更する手段は
用意しない。

1. 未完了タスク（`tasks.md` に書かれている順）
2. レビュー依頼された PR（`Role == "review"`）
3. 自分の PR（`Role == "mine"`）
4. 完了済みタスク

自分で書いた順序に意味があるのでタスクは並べ替えない。PR は「他人を待たせて
いるもの」が先に来るようにする。

### 外部プロセスの起動

`d`（diff）と `a`（AI）は `tea.ExecProcess` を使う。TUI を一旦畳んで
ターミナルを子プロセスに明け渡し、終了したら TUI に戻る。ページャや
`claude` の対話画面がそのまま使える。

`a` の挙動：選択中アイテムの内容（タスクなら本文、PR ならタイトル・URL・
CI 状態）を一時ファイルに書き、`$TK_AI_CMD <一時ファイルパス>` を起動する。
インボックス全体を渡したい場合は `A`（大文字）で全アイテムを書き出す。

## エラー処理

ここは削らない。

| 状況 | 挙動 |
|---|---|
| `gh` が PATH に無い | 下部バーに1行エラー。タスク側は通常どおり動く |
| `gh` が未ログイン | 同上。`gh` の stderr をそのまま出す |
| `gh` がタイムアウト | 10秒で打ち切り、エラー表示。`r` で再試行できる |
| `tasks.md` が無い | 空リストで起動。最初の書き込み時に作成する |
| `tasks.md` が読めない（権限等） | エラーを表示して**起動を中止**する。空リストで起動すると、書き戻し時に既存の内容を消しかねない |
| パースできない行 | `Item` にせず原文のまま保持し、書き戻し時に元の位置へ復元する |

PR の取得失敗でアプリを落とさない。タスク管理は GitHub と無関係に成立する。

## テスト

非自明なロジックは `task.go` のパース・書き戻しだけなので、そこを押さえる。
標準の `testing` のみ。テストフレームワークは足さない。

- **round-trip**: 見出し・コメント・空行・自由記述を含むファイルを読んで
  そのまま書き戻したとき、1バイトも変わらないこと
- **toggle**: 対象行の `[ ]` だけが `[x]` になり、他の行が無傷なこと
- **append**: 新規タスクが末尾のリストブロックに追記され、後続の見出しが
  壊れないこと
- **github**: `gh search prs` の JSON サンプルから `Item` への変換。
  2本のクエリ結果の重複排除を含む

TUI（`ui.go`）のテストは書かない。壊れたら起動すれば分かる。

## 実装順序

1. `task.go` + テスト（ファイル I/O が全ての土台）
2. `item.go` + `ui.go` の最小版（タスクだけ表示・トグル・追加できる）
3. `github.go` + テスト（PR をリストに混ぜる）
4. 右ペインの詳細表示 + PR 情報の遅延補完
5. `ai.go` + `d` キー（外部プロセス起動）

2 の時点で「Markdown タスク管理 TUI」として実用になる。そこで一度使ってみて、
3 以降の優先度を決め直せる。
